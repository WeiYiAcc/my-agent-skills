# 溯源式架构探索（Trace-back Architecture Discovery）

## 何时触发

- 用户抱怨一个**具体的操作摩擦**（不是抽象需求）
- 解决当前问题时发现**下一层问题**（递归追问的信号）
- 需要在多个技术方案间做**选型对比**
- 讨论涉及**跨领域工具组合**（配置语言 + 数据处理 + 编排 + 加密等）

## 核心流程

```
1. 捕捉痛点        → 用户的具体操作摩擦是什么？
2. 追问根因        → 这个摩擦背后的结构性问题是什么？
3. 展开方案空间     → 有哪些技术路径可以解决？
4. 实测验证        → 用真实数据跑一遍，不靠调研堆砌
5. 发现下一层问题   → 解决了当前问题后，暴露了什么新问题？
6. 重复 2-5        → 直到收敛
7. 输出决策        → 架构图 + 工具选型 + 待办清单
```

## 纪律

### 每一层必须做的

- **实测** — 不是"理论上能做"，而是跑一遍看实际效果
- **对比** — 至少两个方案放在一起比较同一个场景
- **记录失败** — 哪个方案试了不行，为什么，写清楚（给未来的自己/AI 看）
- **用户确认** — 每层结论需要用户确认后再进入下一层

### 禁止

- 禁止跳过实测直接给结论（"理论上 X 比 Y 好"→ 不行，跑一遍）
- 禁止一次铺开太多层（一次追问一层，等用户消化）
- 禁止忘记记录（每次收敛时写入 ai-memory + ariadne-fact）

## 追问模式

从用户的每一个「？」出发：

```
用户问：为什么 X 不能做？
  → 分析 X 的设计定位（它是为什么场景设计的）
  → 找到能做的 Y
  → 对比 X 和 Y 在用户场景的实际表现
  → 用户追问下一个「？」
  → 递归
```

## 收敛信号

当满足以下条件时停止递归：

1. 用户说"我有思路了"或"先放放"
2. 当前层的问题需要大量实施工作才能继续探索
3. 已经形成了清晰的多层架构图
4. 待办清单已经可执行

## 产出格式

最终记录必须包含：

```markdown
## 思维链（每层的问题→方案→实测→结论）
## 架构图（多层工具如何组合）
## 工具选型表（职责 | 工具 | 理由）
## 关键测试数据（数字说话）
## 未实施清单（下一步可执行的）
```

## 命名约定

记录到 ai-memory 时：
- 路径：`decisions/<topic>-<date>.md`
- tag：`decision`, `architecture`, 相关工具名
- pinned：true（这类决策长期有效）

记录到 ariadne-fact 时：
- name：`<topic>` kebab-case
- tags：`decision`, `architecture`

## 示例：2026-06-22 配置格式统一化

```
痛点: AI diff 加密文件看不懂
  ↓ 追问
根因: age 整文件加密无结构信息
  ↓ 方案
sops（key 可见 value 加密）
  ↓ 实测通过，但引出新问题
格式太多（yaml/json/toml/edn/env）
  ↓ 追问
能否统一？→ jet 互转 + universal schema
  ↓ 实测通过，但引出新问题
需要校验（不只是格式转换）
  ↓ 方案空间
KCL / CUE / Nickel / Dhall / Pkl
  ↓ 实测（三者都跑了真实数据）
KCL 校验最好，CUE schema 推理独有，Nickel 当前不适用
  ↓ 继续追问
校验 vs 事务性 vs 数据操作 的区别
  ↓ 收敛
多层架构：CUE(分析) → pandas(操作) → KCL(校验) → hook(编排)
```

## 与其他 skill 的关系

| 场景 | 用哪个 skill |
|---|---|
| 已有明确需求，要写代码 | brainstorming → writing-plans → executing-plans |
| 已有 bug，要修复 | systematic-debugging |
| 从痛点出发，不知道该用什么工具/架构 | **trace-back-architecture-discovery** |
| 需要调研某个工具的能力 | web-search + 实测 |
